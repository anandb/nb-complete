Locate any file by name and get the absolute "path" that read_file and open_pos expect — the first step whenever you need a file you cannot already address by absolute path.

Call this FIRST, before list_directory, search_project, or run_command (ls, find, glob, find .): if you only know a file name or fragment — from the user, an import, a stack trace, or a guess — call find_file on it instead of browsing directories, grepping contents, or shelling out. Do NOT use search_project to locate a file by name (it scans file contents and is far slower). For a Java class when you need its fully qualified name or declaration use find_java_type instead; for everything else you address by filename (sources, resources, configs, docs) use this.

A plain query needs at least 3 characters and matches a file-name prefix or any substring of the project-relative path, so ChatPanel finds ChatPanel.java and ui/chat hits everything under that path. A query with glob characters (*, ?, [, {) is matched bash-style against the file name and the relative path with an implicit trailing *, so *Test finds MyTestFile.java, *.java finds Java sources, and **/main/** stays inside a directory. Globs work at any length.

It answers instantly from the IDE's file index — no disk scan — searching this session's working directory by default (reply says "scope": "session" with "directory"). Pass "scope": "projects" to search every open project instead; a session with no working directory already searches them all, and if nothing inside the working directory matches the search widens to all open projects and reports "widened": true. The index respects the project's VCS ignore rules (.gitignore, .hgignore, .bbignore), so ignored files and build output are never returned.

Up to 5 matches are returned, file-name hits ranked first, each with "name", "project", "relativePath", and absolute "path". "truncated": true means more files matched than the 5 returned — narrow the query. "indexing": true means the index is still building, so retry shortly.
